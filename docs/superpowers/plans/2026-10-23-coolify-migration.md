# ABL 官网迁入 Coolify 实施计划

> 执行者：按 `superpowers:executing-plans` 逐项执行并更新复选框。默认由主 agent 执行，不自动委派。用户已授权开始实施；正式停机窗口仍按本计划确认。

**目标：** 将前端 Nginx、Strapi、PostgreSQL 统一交给现有 Coolify 管理，保留网站内容、后台账号、媒体、域名与使用方式。

**已确认路线：** 同一台 VPS 上使用 Git 来源的 Docker Compose，沿用 PostgreSQL 数据卷与上传目录；通过 Coolify 的 Traefik 提供正式入口。

**自动部署：** 用户追加要求将 GitHub push 后的部署纳入 Coolify。迁移验收后启用正式 `main` 分支自动部署，仓库由现有 GitHub App 来源读取，push 通知使用 Coolify 原生的仓库签名 webhook，不新增 GitHub Actions 或镜像仓库流程。迁移分支和前端改版分支不触发生产部署。

## 已确认的部署决策

| 决策 | 本次选择 |
|---|---|
| 构建位置 | Coolify 在同一台生产机从 Git 构建前后端 Docker 镜像；不使用 Actions 构建及远端镜像推送链路 |
| 前端 | 继续以 Nginx 容器提供 Vue 构建产物 |
| Strapi | 从宿主机 root PM2 迁入独立容器；镜像内完成编译及管理后台构建，直接执行 `strapi start`，容器内不再安装 PM2 |
| 数据库 | 保持 PostgreSQL 16，沿用现有数据卷，不新建空库替代正式库 |
| 数据与秘密 | 原上传目录持久挂载，原 Strapi 密钥保留，真实环境变量由 Coolify 保密配置 |
| 正式发布 | 迁移验收后，`main` push 触发 Coolify 构建和发布整套 Compose 应用 |

Strapi 容器的重启策略和 Coolify 接替 PM2 的运行管理职责；旧 PM2 进程只在正式切换时停止，定义保留供回退。

**技术栈：** Vue 3 / Vite、Strapi 5.23.3、Node 22、PostgreSQL 16、Nginx、现有 Coolify / Traefik。此次不升级业务依赖或数据库主版本。

**依据：** 本次对 `ali-deploy`、`ali-root` 的只读调查及用户对三服务迁移路线的确认；执行前同时读取 `/data/sunyunbo/.codex/memories/coolify-deployment.md` 的最新内容。

## 范围与执行约束

- 本文中尚未实施的配置均为计划；具体停机窗口在正式切换前与用户确认。
- 不混入前端改版、内容模型调整、数据库升级、对象存储、新备份平台或新的 CI 系统。
- 先准备和演练，再安排一次短暂停机切换；不为本次低频网站增加双写、增量同步或自动故障恢复机制。
- 保留所有 Strapi 密钥，不重新生成；数据库内容、账号和权限不通过 Git 恢复。
- 不输出密钥、完整 `docker inspect` 环境变量或带真实变量的 Compose 展开结果；配置检查使用 `docker compose ... config --quiet`。
- 演练环境只用数据副本，不连接正式库，不挂载正式上传目录写入；不把后台和数据库开放到公网。
- 正式卷 `abl_website_pgdata` 只能由一个 PostgreSQL 实例使用；切换和回退都先停当前实例，再启动另一实例。
- 不删除旧容器、数据库卷、上传目录、备份或 PM2 保存配置；不执行 `docker compose down -v`。
- 不重置共享 Traefik，不恢复旧 Nginx 公网监听，不改其他应用或 root 的整个 PM2 服务。
- 默认运行相关已有检查、构建和只读 HTTP 验证；不新增端到端测试项目，不自动登录、点击或提交生产表单。

## 目标配置及文件职责

拟使用三个服务：`frontend`、`strapi`、`postgres`。为保留现有代理和静态媒体行为，计划由前端现有 Nginx 同时承接前端域名及 API 域名：前端提供静态页面，API 转给 Strapi，`/uploads/` 从只读挂载提供。Traefik 负责 TLS。图片加速域名继续使用现有 ESA。

这沿用现有三服务边界；Nginx 只是承接原宿主规则，不新增第四个网关服务。正式库通过 Compose 内部 `postgres:5432` 访问，不发布数据库或 Strapi 宿主端口。

| 文件 | 计划职责 |
|---|---|
| `docker-compose.coolify.yml`（新增） | 三服务、内部网络、外部原数据库卷、上传挂载和必要健康检查 |
| `.env.coolify.example`（新增） | 无密钥的变量名及说明，区分构建变量与运行变量 |
| `strapi-backend/Dockerfile`（修改） | Node 22 构建、编译 Strapi 和后台、运行生产服务；验证原生依赖和上传写权限 |
| `strapi-backend/.dockerignore`（按需修改） | 保证真实环境文件、数据库和媒体不进入镜像 |
| `frontend/Dockerfile`（按需修改） | 支持 Coolify 专用 Nginx 配置，保留普通部署用途 |
| `frontend/nginx.coolify.conf`（新增） | 前端、API、静态媒体规则；配置随镜像构建，避免平台单文件挂载问题 |
| `update.sh`、`update-strapi.sh`、`deploy.sh`（修改） | 切换后检测标记 `/home/deploy/abl_website/.coolify-managed`，拒绝旧发布路径 |
| `docs/deployment/coolify.md`（新增） | 日常部署、变量、数据路径、验收、备份位置及人工回退说明 |

实施时先核对官方 Node 22 镜像可用版本与原生依赖，优先匹配当前 22.23.4 并记录 digest；不为了修复镜像构建问题顺便升级 Strapi。若必须更换重要依赖或调整服务边界，先提交用户决定。

## 验收边界

完成标准：代码基线未混入改版；三个服务由 Coolify 管理；原内容、媒体和账号数据保留；五个域名及图片域名可用；旧入口与旧进程不再竞争；备份能恢复、回退步骤可审查；正式 main 的 push 自动部署已配置，并说明实际触发是否验证。

本计划不要求压力测试、服务器重启、实际生产回退或等待证书到期续期；未进行的验证在交付记录中明确说明。配置检查、已有检查和必要的 HTTP 验收通过后结束验证，不反复扩大范围。
